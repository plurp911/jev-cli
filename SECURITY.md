# Security Policy

`jev` handles API credentials and sends user-supplied content to a third-party service.
Both make it a meaningful target. Security reports are welcome and will be taken
seriously.

## Reporting a vulnerability

**Do not open a public issue for a security vulnerability.**

Report privately through GitHub Security Advisories:

<https://github.com/plurp911/jev-cli/security/advisories/new>

Please include what you can: affected version and platform, what an attacker gains,
reproduction steps or a proof of concept, and anything you know about exploitability.
A partial report is better than no report.

**Never include a real API key**, your own or anyone else's, in a report. Use an
obviously fake placeholder.

### What to expect

| Stage | Target |
| --- | --- |
| Acknowledgement | 3 working days |
| Initial assessment | 10 working days |
| Fix or mitigation for a confirmed high-severity issue | 30 days |

This is a volunteer community project with no commercial support. These are honest
targets, not a contractual commitment.

We will credit you in the advisory unless you ask us not to. There is no bug bounty.

### Coordinated disclosure

We ask for 90 days before public disclosure, or until a fix ships, whichever comes
first. If a vulnerability is being actively exploited, tell us and we will move faster.

## Scope

**In scope** — anything in this repository, including:

- Disclosure of credential material through any channel: output, logs, errors, panics,
  temporary files, process arguments, or environment propagation.
- Sending a credential to a host other than the one the user intended.
- Memory-safety or resource-exhaustion problems reachable from untrusted input, such as
  an API response, stdin, or a file.
- Terminal escape or control-character injection through displayed content.
- Path traversal, symlink following, or writing outside a user-specified location.
- Weaknesses in the release pipeline, workflow permissions, or artifact integrity.
- Dependency vulnerabilities that are actually reachable from `jev`.

**Out of scope**:

- Vulnerabilities in the TypeSafe API or service itself. Report those to TypeSafe.
- Anything requiring an already-compromised machine or a malicious local administrator.
- Missing hardening with no demonstrable impact.
- Reports generated by a scanner with no analysis of reachability.
- Social engineering of maintainers.

## Security properties `jev` aims to provide

These are commitments. A deviation from any of them is a vulnerability, not a bug.

1. **A credential never appears in any output stream** — stdout, stderr, an error
   message, or a panic payload — under any invocation, including failures.
2. **A credential is never accepted as a command-line argument**, because arguments are
   visible in the process table, in shell history, and in CI logs.
3. **A credential is never written to disk in plaintext by `jev`.** There is no silent
   plaintext fallback: if secure storage is unavailable, `jev` fails with an actionable
   error and points the user at environment-based authentication.
4. **A credential is only ever sent to the endpoint the user configured**, and any
   non-default endpoint is visible in output rather than silently inherited.
5. **`jev` transmits only what the user explicitly supplied.** It does not read
   unnamed files, does not walk directories, and does not load `.env` files.
6. **`jev` collects no telemetry**, sends no analytics, and makes no network request
   that the user did not ask for.
7. **`jev` executes no code from configuration, input, or a plugin.** There is no
   plugin system.
8. **Untrusted content is sanitized before display**, so a response cannot rewrite the
   user's terminal.
9. **`jev` contains no `unsafe` Rust.** The workspace sets `unsafe_code = "forbid"`.

The reasoning behind these, and the attacks they are meant to stop, is in
[`docs/threat-model.md`](docs/threat-model.md).

## Supported versions

Only the latest published release is supported. This will be revised when the project
reaches 1.0.

## Supply chain

- All third-party GitHub Actions are pinned to immutable commit SHAs.
- Workflow permissions are least-privilege and default to `permissions: {}`.
- Contributors run `scripts/verify.sh --push` before pushing. It audits workflows with
  [zizmor](https://docs.zizmor.sh), checks dependencies with `cargo-deny`, and runs the
  credential canary. The local hook can be bypassed; GitHub runs no automatic CI for
  this repository.
- `Cargo.lock` is committed and local verification builds with `--locked`.
- The manual release workflow builds checksums and an SBOM. Publication requires build
  provenance, which must be checked on each published release; see
  [ADR-0014](docs/adr/0014-manual-release-gate.md).

If you believe a dependency or a release artifact has been compromised, report it
through the same private channel above.
